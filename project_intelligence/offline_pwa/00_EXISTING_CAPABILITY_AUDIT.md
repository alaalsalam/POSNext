# Phase 7A Existing Offline/PWA Capability Audit

Target: `pos.yemenfrappe.com` / `apps/pos_next`

## 1. PWA

- Manifest support exists through `vite-plugin-pwa` in `POS/vite.config.js`.
- The built `/pos` HTML links `/assets/pos_next/pos/manifest.webmanifest`.
- The generated manifest currently includes `name`, `short_name`, `description`, `start_url: /pos`, `display: standalone`, theme/background colors, and SVG icons.
- Icons exist in `POS/public/icon.svg`, `POS/public/icon-maskable.svg`, and `POS/public/favicon.png`.
- Installability is mostly present, but the generated manifest currently declares `scope: /assets/pos_next/pos/` while `start_url` is `/pos`. That makes the app scope inconsistent with the user-facing POS route and can weaken installability/routing behavior.
- `POS/manifest.webmanifest` also exists as a legacy/static manifest and is out of sync (`start_url: "."`, root favicon paths). It is not the primary generated manifest, but keeping it stale is confusing.

## 2. Service Worker

- Service Worker support exists through `VitePWA` and `virtual:pwa-register` in `POS/src/main.js`.
- The built service worker is available at `/assets/pos_next/pos/sw.js`.
- Workbox is configured for:
  - precaching build assets,
  - static POS assets with `CacheFirst`,
  - product images with `StaleWhileRevalidate`,
  - API calls with `NetworkFirst`,
  - `/pos` navigations with `NetworkFirst`,
  - old cache cleanup,
  - `skipWaiting`,
  - `clientsClaim`.
- The app logs update/offline-ready events, but does not present a dedicated update prompt.
- Risk: because the generated service worker is served from `/assets/pos_next/pos/sw.js`, its effective browser scope may remain asset-scoped unless server headers allow a wider scope. This is a deployment/header concern and should not be rewritten in this phase.
- Risk: `sw.js` is served with long asset caching headers, which can delay service-worker updates. This is a deployment/header concern because it comes from the Frappe assets path.

## 3. IndexedDB / Local Storage

- IndexedDB exists through Dexie in `POS/src/utils/offline/db.js`.
- Main database: `pos_next_offline`.
- Stores include:
  - `settings`
  - `invoice_queue`
  - `items`
  - `customers`
  - `item_prices`
  - `stock`
  - `payment_methods`
  - `sales_persons`
  - `payment_queue`
  - `drafts`
  - `translations`
  - `offers`
  - `invoice_history`
  - `unpaid_invoices`
- A separate draft IndexedDB helper exists in `POS/src/utils/draftManager.js` with database `pos_next_drafts`.
- Current cart data is not automatically persisted as a recovery snapshot; drafts exist, but a cashier can still lose an unsaved active cart on refresh/crash unless it has been saved manually.

## 4. Offline Sales

- Offline invoice queue exists in `POS/src/utils/offline/sync.js`.
- Offline invoices are saved with unique `offline_id` generated by `POS/src/utils/offline/uuid.js`.
- The queue preserves `data`, `timestamp`, `synced`, and `retry_count`.
- Local stock is decremented optimistically after saving an offline invoice.
- `OfflineInvoicesDialog.vue` displays pending invoices and allows manual sync, print, edit, and delete.
- Failed invoices are preserved, but the visible error reason is weak until max retry failure.

## 5. Sync

- Sync exists through `syncOfflineInvoices()`.
- Sync is called manually from the POS UI and automatically when `offlineState` transitions from offline to online.
- A coalescing mutex prevents concurrent sync runs.
- Sync performs a preflight duplicate check before submit.
- Failed sync attempts increment `retry_count`; after max retries the invoice is marked failed in IndexedDB.

## 6. Idempotency

- Client-side offline IDs exist.
- Server-side duplicate prevention exists in `pos_next.api.invoices.submit_invoice`.
- Backend uses DocType `Offline Invoice Sync` with unique `offline_id`.
- `_ensure_offline_uniqueness()` uses a pending reservation pattern and row-level locking.
- Re-submitting the same offline invoice returns the existing submitted Sales Invoice instead of creating a duplicate.
- This is already strong and does not need a schema change in Phase 7A.

## 7. UX

- Header shows online/offline status and pending invoice count.
- Header shows cache status and last sync inside a tooltip.
- Offline invoices dialog shows pending invoices and retry count.
- Install prompt exists through `InstallAppBadge.vue`.
- Missing/weak:
  - no clear active cart recovery indicator,
  - stale cache age is not strongly highlighted,
  - failed sync error reason is not easy for a cashier to see.

## 8. Long Offline Usage

- Cached data can remain usable for offline search and sale.
- Product image cache expires after 7 days.
- API cache expires after 24 hours.
- POS asset cache expires after 30 days.
- There is no explicit cashier-facing warning for 1/3/7 day stale item/price/stock cache.

## 9. Risks

- Data loss risk: unsaved active cart can be lost on refresh/crash.
- Duplicate invoice risk: already mitigated by `offline_id` and backend `Offline Invoice Sync`.
- Confusion risk: cashier may not know data is stale after long offline use.
- Sync troubleshooting risk: failed invoice error reason is not visible enough in the pending invoice list.
- Safe now:
  - Dexie/offline worker/outbox/idempotency already exist.
  - No new IndexedDB layer, outbox, service worker, or backend schema is needed for Phase 7A.
